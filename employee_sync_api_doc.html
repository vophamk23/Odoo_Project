API 1 — ControllerEmployeeSync

Trả về danh sách Nhân viên cần đồng bộ xuống Controller phần cứng, sử dụng phân trang dựa trên Cursor để đảm bảo dữ liệu nhất quán giữa các trang.

Endpoint Name: ControllerEmployeeSync

Method: POST

Content-Type: application/json

1.1 Tham Số Đầu Vào (Request Body)

ParameterTypeRequiredDefaultDescription
controller_snString Bắt buộc— Mã sê-ri phần cứng của Controller.
last_sync_atString Tùy chọnnull Mốc thời gian đồng bộ thành công gần nhất (YYYY-MM-DD HH:MM:SS).
Nếu không truyền → server đồng bộ toàn bộ nhân viên.
page_sizeInteger Tùy chọn15 Số lượng bản ghi tối đa trả về trong 1 trang.
next_cursor_idInteger Tùy chọnnull ID cursor nhận từ trang trước. Không truyền ở trang đầu tiên.
latest_write_dateString Tùy chọnnull Mốc write_date của cursor nhận từ trang trước. Truyền kèm next_cursor_id.

▸ Request — Trang đầu tiên (Đồng bộ lần đầu):

{
  "controller_sn": "CTRL_001",
  "page_size": 15
}

▸ Request — Trang đầu tiên (Incremental sync từ lần 2):

{
  "controller_sn": "CTRL_001",
  "last_sync_at": "2026-07-25 08:00:00",
  "page_size": 15
}

▸ Request — Trang tiếp theo (Sử dụng cursor):

{
  "controller_sn": "CTRL_001",
  "last_sync_at": "2026-07-25 08:00:00",
  "page_size": 15,
  "next_cursor_id": 42,
  "latest_write_date": "2026-08-01 10:30:00"
}

1.2 Cấu Trúc Phản Hồi (Response Body)

{
  "success": true,
  "message": "Employee sync completed",
  "data": {
    "data": {
      "next_cursor_id": 42,
      "has_next_page": true,
      "new": [ ... ],
      "update": [ ... ],
      "deleted": [ ... ],
      "latest_write_date": "2026-08-01 10:30:00"
    }
  }
}

Chi tiết các field trong data.data:

FieldTypeDescription
next_cursor_idInteger / nullID bản ghi cuối cùng trong trang. Truyền lại cho trang tiếp theo. null nếu không còn trang sau.
has_next_pageBooleantrue nếu còn trang tiếp; false nếu đã hết dữ liệu.
newArrayDanh sách nhân viên mới thêm (tạo sau last_sync_at hoặc toàn bộ nếu sync lần đầu).
updateArrayDanh sách nhân viên đã tồn tại nhưng có cập nhật thông tin.
deletedArrayDanh sách nhân viên bị vô hiệu hóa (active = False).
latest_write_dateStringMốc write_date mới nhất trong lô dữ liệu (YYYY-MM-DD HH:MM:SS).
Controller lưu lại giá trị này làm last_sync_at cho đợt sync tiếp theo.

Cấu trúc Object Nhân Viên (trong new, update, deleted):

FieldTypeDescription
idIntegerMã định danh duy nhất của nhân viên (emp_id).
nameStringTên đầy đủ của nhân viên.
branch_idInteger / nullID Chi nhánh. null nếu thuộc tất cả chi nhánh.

1.3 Cơ Chế Phân Trang Cursor (Pagination Flow)

Tại sao dùng Cursor? Cursor-based pagination đảm bảo không bỏ sót và không trùng lặp bản ghi giữa các trang, ngay cả khi có dữ liệu mới thay đổi trên Server trong lúc Controller đang kéo từng trang.
  1. Trang đầu tiên: Controller gọi API không truyền next_cursor_id và latest_write_date.
  2. Kiểm tra has_next_page:
    • Nếu true: Lưu next_cursor_id + latest_write_date từ response, truyền lại vào request trang tiếp theo.
    • Nếu false: Hoàn tất. Lưu latest_write_date làm last_sync_at cho đợt đồng bộ sau.

1.4 Response Mẫu

▸ Trường hợp 1 — Còn trang tiếp (has_next_page = true):

{
  "success": true,
  "message": "Employee sync completed",
  "data": {
    "data": {
      "next_cursor_id": 42,
      "has_next_page": true,
      "new": [
        { "id": 1001, "name": "Nguyen Van A", "branch_id": 2 },
        { "id": 1002, "name": "Tran Thi B", "branch_id": null }
      ],
      "update": [],
      "deleted": [],
      "latest_write_date": "2026-08-01 10:30:00"
    }
  }
}

▸ Trường hợp 2 — Trang cuối (has_next_page = false):

{
  "success": true,
  "message": "Employee sync completed",
  "data": {
    "data": {
      "next_cursor_id": null,
      "has_next_page": false,
      "new": [],
      "update": [
        { "id": 1003, "name": "Le Van C", "branch_id": 2 }
      ],
      "deleted": [
        { "id": 999, "name": "Pham Van D", "branch_id": 2 }
      ],
      "latest_write_date": "2026-08-03 14:00:00"
    }
  }
}

API 2 — EmployeeBiometricUpdate

Nhận dữ liệu sinh trắc học (Vân tay, Khuôn mặt, Ảnh đại diện) và thông tin cơ bản của nhân viên từ Controller, lưu / cập nhật vào Server.
Nếu nhân viên chưa tồn tại trên hệ thống, sẽ tự động tạo mới.

Endpoint Name: EmployeeBiometricUpdate

Method: POST

Content-Type: application/json

2.1 Tham Số Đầu Vào (Request Body)

ParameterTypeRequiredDescription
controller_snString Bắt buộc Mã sê-ri phần cứng của Controller.
USERObject Bắt buộc Khối thông tin nhân viên (xem chi tiết bên dưới).
FPArray Tùy chọn Danh sách mẫu vân tay.
BIODATAObject Tùy chọn Mẫu khuôn mặt (Face template).
PHOTOObject Tùy chọn Ảnh đại diện của nhân viên.

Cấu trúc khối USER:

FieldTypeRequiredDescription
PINIntegerBắt buộcMã nhân viên (emp_id). Dùng để định danh.
NameStringTùy chọnTên nhân viên.
PasswdStringTùy chọnMật khẩu truy cập thiết bị.
CardIntegerTùy chọnSố thẻ serial (RFID / NFC).
PriIntegerTùy chọnQuyền hạn truy cập (privilege level).

Cấu trúc mỗi phần tử trong mảng FP (Fingerprint):

FieldTypeDescription
FIDIntegerChỉ số ngón tay / slot (thường 0–9).
TMPString (Base64)Chuỗi mẫu vân tay đã mã hóa.

Cấu trúc khối BIODATA (Face):

FieldTypeDescription
IndexIntegerChỉ số slot khuôn mặt.
TmpString (Base64)Chuỗi mẫu khuôn mặt đã mã hóa.

Cấu trúc khối PHOTO:

FieldTypeDescription
ContentString (Base64)Ảnh đại diện nhân viên đã mã hóa Base64.

2.2 Request Mẫu

▸ Request đầy đủ (Tạo/Cập nhật NV + Vân tay + Khuôn mặt + Ảnh):

{
  "controller_sn": "CTRL_001",
  "USER": {
    "PIN": 1001,
    "Name": "Nguyen Van A",
    "Passwd": "123456",
    "Card": 88001234,
    "Pri": 0
  },
  "FP": [
    { "FID": 0, "TMP": "RklOR0VSUF...base64data..." },
    { "FID": 1, "TMP": "RklOR0VSUF...base64data..." }
  ],
  "BIODATA": {
    "Index": 0,
    "Tmp": "RkFDRVRFTVBMQVRF...base64data..."
  },
  "PHOTO": {
    "Content": "iVBORw0KGgo...base64data..."
  }
}

▸ Request tối thiểu (Chỉ cập nhật thông tin cơ bản):

{
  "controller_sn": "CTRL_001",
  "USER": {
    "PIN": 1001,
    "Name": "Nguyen Van A Updated"
  }
}

2.3 Luồng Xử Lý Nghiệp Vụ

  1. Xác thực Controller: Kiểm tra controller_sn tồn tại trên hệ thống.
  2. Tìm nhân viên theo USER.PIN (emp_id) trong phạm vi chi nhánh của Controller.
    • Nếu tìm thấy → cập nhật các trường thông tin được truyền lên (Name, Passwd, Card, Pri).
    • Nếu không tìm thấy → tự động tạo mới bản ghi nhân viên, gán branch_id theo chi nhánh của Controller.
  3. Xử lý Vân tay (FP): Duyệt từng phần tử → tìm bản ghi Biometric theo (employee_id, fingerprint, FID).
    • Nếu tồn tại → write() cập nhật template.
    • Nếu chưa có → create() tạo mới.
  4. Xử lý Khuôn mặt (BIODATA): Tương tự Vân tay, tìm theo (employee_id, face, Index).
  5. Xử lý Ảnh (PHOTO): Nếu có Content → ghi trực tiếp vào trường avatar của nhân viên.
Lưu ý: API này không trả về response body (void). Framework t4_coreapi sẽ tự động bọc thành { "success": true, "message": "Successful" }.

2.4 Response Mẫu

▸ Thành công:

{
  "success": true,
  "message": "Successful"
}

Xử Lý Lỗi Chung (Error Handling)

Khi xảy ra lỗi validation, hệ thống trả về JSON với success: false kèm thông báo lỗi thân thiện. Không bao giờ trả về Python traceback.

Cấu trúc Response lỗi:

{
  "success": false,
  "message": "Nội dung mô tả lỗi"
}

Các trường hợp lỗi chung (áp dụng cả 2 API):

#Trường hợpMessage trả về
1Thiếu controller_sn"Controller ID is required."
2Controller không tồn tại"Can not find controller with ID {sn}"

Lỗi riêng API ControllerEmployeeSync:

#Trường hợpMessage trả về
3Sai định dạng last_sync_at"Invalid last sync time format. Expected YYYY-MM-DD HH-MM-SS"
4page_size không phải số hoặc < 1"Invalid page size"
5Sai định dạng latest_write_date"Invalid latest_write_date"
6next_cursor_id không phải số"Invalid cursor id"

Lỗi riêng API EmployeeBiometricUpdate:

#Trường hợpMessage trả về
7Thiếu khối USER"User information is required"
8Thiếu USER.PIN"Missing employee id"
